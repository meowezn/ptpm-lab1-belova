## 1. Назначение и границы ответственности

«Сервис задач» — консольный модуль Python для студента. Модуль позволяет создавать задачи, просматривать и изменять их, выполнять поиск и сохранять данные в JSON-файл.

### Входит в границы модуля
- создание задач;
- получение задачи по идентификатору;
- просмотр списка;
- изменение названия и описания;
- изменение статуса;
- фильтрация по статусу;
- поиск по ключевому слову;
- загрузка из JSON;
- сохранение в JSON;
- управляемая обработка ошибок.

### Не входит в границы модуля
- графический/веб-интерфейс;
- регистрация и аутентификация;
- права доступа;
- сетевое взаимодействие;
- синхронизация между устройствами;
- уведомления;
- совместное редактирование.

## 2. Вопросы аналитика и принятые решения

1. **Сколько задач может быть у пользователя?** — не более 10 000. Попытка создать 10 001-ю отклоняется.
2. **Какие статусы допустимы?** — только `new`, `in_progress`, `done`.
3. **Можно ли менять текст задачи после создания?** — да, название и описание можно изменить по ID; ID не меняется.
4. **Как определяется уникальность?** — по идентификатору. Названия могут повторяться.
5. **Что делать, если JSON-файл отсутствует?** — считать хранилище пустым и не выдавать ошибку при старте; файл создаётся при первом успешном сохранении.
6. **Что делать, если JSON-файл повреждён?** — вернуть `DataFileCorrupted` и не перезаписывать исходный файл автоматически.
7. **Что считается успешным сохранением?** — JSON-файл полностью записан без ошибки и содержит актуальное состояние задач.
8. **Учитывается ли регистр при поиске?** — нет, поиск регистронезависимый.
9. **По каким полям выполняется поиск?** — по названию и описанию.
10. **Какой статус получает новая задача?** — `new`.
11. **Может ли название быть пустым?** — нет, пустая строка и строка только из пробелов недопустимы.
12. **Может ли описание быть пустым?** — да.

## 3. Функциональные требования

### R-01. Создание задачи
Система должна позволять создать задачу с названием и описанием.  
**Проверка:** после создания задача появляется в списке с переданными названием и описанием.

### R-02. Уникальный идентификатор
Система должна назначать каждой новой задаче непустой уникальный идентификатор.  
**Проверка:** создать две задачи и убедиться, что их ID не пустые и различаются.

### R-03. Начальный статус
Новая задача должна получать статус `new`.  
**Проверка:** создать задачу и проверить её статус.

### R-04. Получение по ID
Система должна возвращать задачу по существующему идентификатору.  
**Проверка:** передать ID существующей задачи и получить именно эту задачу.

### R-05. Просмотр списка
Система должна возвращать список всех существующих задач.  
**Проверка:** создать несколько задач и убедиться, что все они присутствуют в списке.

### R-06. Изменение названия
Система должна позволять изменить название существующей задачи.  
**Проверка:** изменить название и повторно получить задачу по тому же ID.

### R-07. Изменение описания
Система должна позволять изменить описание существующей задачи.  
**Проверка:** изменить описание и проверить новое значение.

### R-08. Изменение статуса
Система должна позволять установить статус `new`, `in_progress` или `done`.  
**Проверка:** установить допустимый статус и убедиться, что он отображается у задачи.

### R-09. Фильтрация по статусу
Система должна возвращать только задачи с указанным допустимым статусом при использовании фильтра.  
**Проверка:** создать задачи с разными статусами и проверить состав отфильтрованного списка.

### R-10. Поиск по ключевому слову
Система должна искать ключевое слово в названии и описании задачи.  
**Проверка:** выполнить поиск слова, присутствующего только в названии, а затем только в описании.

### R-11. Регистронезависимый поиск
Поиск не должен зависеть от регистра букв.  
**Проверка:** выполнить один поиск в нижнем регистре и один в верхнем и сравнить результаты.

### R-12. Пустой результат поиска
При отсутствии совпадений система должна возвращать пустой список без ошибки.  
**Проверка:** искать слово, отсутствующее во всех задачах.

### R-13. Сохранение в JSON
Система должна сохранять актуальный набор задач в JSON-файл.  
**Проверка:** сохранить задачи и проверить наличие актуальных полей в JSON.

### R-14. Загрузка из JSON
Система должна загружать задачи из корректного JSON-файла при запуске/инициализации.  
**Проверка:** сохранить задачи, повторно запустить модуль и проверить восстановленные данные.

### R-15. Отсутствующий файл
При отсутствии JSON-файла система должна использовать пустой набор задач без аварийного завершения.  
**Проверка:** удалить файл, запустить модуль и получить пустой список.

### R-16. Лимит задач
Система должна разрешать не более 10 000 задач.  
**Проверка:** 10 000 задач создаются успешно, 10 001-я отклоняется.

### R-17. Стабильность ID
При изменении названия, описания или статуса ID задачи не должен изменяться.  
**Проверка:** сохранить ID до изменения и сравнить его после изменения.

### R-18. Повторное сохранение
После изменения задачи система должна сохранять обновлённые данные.  
**Проверка:** изменить задачу, сохранить, перезапустить и проверить обновлённые поля.

## 4. Требования к данным и JSON

Файл хранится по пути, переданному модулю как путь к хранилищу.

Корень JSON должен иметь ключ `tasks` со значением-массивом:

```json
{
  "tasks": [
    {
      "id": "1",
      "title": "Подготовить лабораторную",
      "description": "Оформить требования и сценарии",
      "status": "new"
    }
  ]
}
```

Обязательные поля:
- `id`: непустая строка;
- `title`: непустая после удаления пробелов строка;
- `description`: строка, может быть пустой;
- `status`: одно из `new`, `in_progress`, `done`.

Пустое хранилище:

```json
{
  "tasks": []
}
```

## 5. Ошибки

| Код | Условие | Проверяемое поведение |
|---|---|---|
| `EmptyTitle` | Пустое название или только пробелы | Операция отклоняется, данные не изменяются. |
| `InvalidStatus` | Недопустимый статус | Операция отклоняется, прежний статус сохраняется. |
| `TaskNotFound` | ID не существует | Возвращается управляемая ошибка. |
| `TaskLimitExceeded` | Больше 10 000 задач | Новая задача не создаётся. |
| `DataFileCorrupted` | Некорректный JSON/структура | Загрузка не считается успешной, файл не перезаписывается автоматически. |
| `DataFileReadError` | Файл нельзя прочитать | Возвращается управляемая ошибка чтения. |
| `DataFileWriteError` | Файл нельзя записать | Сохранение считается неуспешным, возвращается управляемая ошибка. |

## 6. Ограничения и допущения

1. Рассматривается один логический пользователь.
2. Максимум — 10 000 задач.
3. Названия могут повторяться.
4. ID уникален внутри хранилища.
5. Новая задача получает `new`.
6. Поиск регистронезависимый и идёт по названию и описанию.
7. Отсутствие совпадений — не ошибка.
8. Отсутствие файла — пустое хранилище.
9. Повреждённый файл не перезаписывается автоматически.
10. Используется локальный JSON-файл.
11. Интерфейс не входит в модуль.

## 7. Критерии приёмки

- **AC-01:** корректная задача создаётся, получает уникальный ID и статус `new`.
- **AC-02:** после сохранения и повторной загрузки поля и статус задачи не теряются.
- **AC-03:** допустимый статус меняется, недопустимый — отклоняется без изменения данных.
- **AC-04:** поиск работает по названию и описанию независимо от регистра.
- **AC-05:** пустое название, неизвестный ID и превышение лимита обрабатываются управляемыми ошибками.
- **AC-06:** отсутствующий файл создаёт пустое хранилище, повреждённый JSON вызывает `DataFileCorrupted`.
